# search/v1

Named buckets of content an app searches. An app makes the bucket it needs (`ensure`) and searches it; its admins load
documents into it (files or pasted text, by name). The provider splits each document into chunks that keep their
source (document, section, lines), embeds them with the bucket's model when it has one, and returns the best chunks for
a query, best first. It never answers the question itself: the caller builds the prompt from the results.

A wire contract at `/api/_c/search/v1` ([search.go](search.go)), one provider. The [search](../../../search/README.md)
extension provides it. It brings the dashboard's **Search** screen ([ui/main.js](ui/main.js)), which calls only this
contract, so it works whoever provides it.

## Use

In page code it's `$search` (bound by the search extension):

```js
$search.ensure({ name: "storytime", title: "Story Time library", description: "Stories to draw on." })
const r = await $search.searchAsync({ bucket: "storytime", query: "a fox by the sea", limit: 5 })
r.results[0].text
```

Over HTTP (a superuser, or a token with the scope shown):

| Operation | HTTP | Body | Token scope |
|---|---|---|---|
| Buckets | `GET /api/_c/search/v1/buckets` | | `search:read` |
| Bucket | `GET /api/_c/search/v1/bucket` | `?name=` | `search:read` |
| Ensure | `POST /api/_c/search/v1/ensure` | `{"name", "title", "description", "owner", "model", "dimensions"}` | `search` |
| Update | `POST /api/_c/search/v1/update` | `{"name", "title"?, "description"?, "model"?, "dimensions"?, "maxDocuments"?, "maxBytes"?}` | `search` |
| Delete | `POST /api/_c/search/v1/delete` | `{"name"}` | `search` |
| Add | `POST /api/_c/search/v1/add` | `{"bucket", "name", "text"}` | `search` |
| Upload | `POST /api/_c/search/v1/upload` | `?bucket=&name=`, the file as the body | `search` |
| Documents | `GET /api/_c/search/v1/documents` | `?bucket=&prefix=` | `search:read` |
| Remove | `POST /api/_c/search/v1/remove` | `{"bucket", "names": [...]}` | `search` |
| Reindex | `POST /api/_c/search/v1/reindex` | `{"bucket", "names": [...]}` (none: all) | `search` |
| Search | `POST /api/_c/search/v1/search` | `{"bucket", "query", "limit", "mode", "prefix"}` | `search:read` |

Search answers `{"results": [{"text", "document", "heading", "startLine", "endLine", "score", "semantic", "keyword"}],
"mode", "model", "usage", "note"}`. `mode` is `hybrid` (the default: meaning and keywords merged), `semantic` or
`keyword`; a bucket without a model is searched by keywords, and a hybrid search whose query can't be embedded falls
back to keywords and says why in `note`. Add returns the document with `status` `queued`, `embedding`, `ready` or
`error`, and `unchanged` when the same text was already there.

Errors: `not_found` (no such bucket or document), `bad_request` (a bad name, an empty query, binary content),
`too_large` (over the bucket's limits, or a document over 10 MB), and llm.embed/v1's errors from a semantic search.

From Go: `searchv1.Contract.Must(app)` (from `pocketone.dev/ext/contracts/search/v1`).

## Provide

Implement `searchv1.Search` and provide it in `Register` (`searchv1.Contract.Provide(app, impl)`). Keep these promises:

- `Ensure` is idempotent: an existing bucket keeps its settings; only an empty title, description or owner is filled in.
- `Add` with the same name replaces the document; the same text again changes nothing and says `unchanged`.
- Vectors from two models never mix: a new model or dimensions embeds every chunk again.
- Results are chunks with their source, best first, at most `limit` (default 5, at most 50); `score` orders them.
- Searching is the only operation that may call a model; adding returns before embedding is done.
